# ADR-0001: 持久化与数据库迁移策略

## 状态

Accepted

## 背景

当前 WMS MVP 使用内存仓储，适合验证入库、出库、库存查询和库存流水规则。但 WMS 的核心价值依赖库存准确性和审计可追踪，下一阶段必须引入数据库持久化和可重复执行的 schema 迁移机制。

## 决策

1. 使用 Flyway 兼容的 `src/main/resources/db/migration/V{version}__{description}.sql` 目录组织迁移脚本。
2. 以 PostgreSQL 作为优先设计方言，并保留 MySQL 兼容演进空间。
3. 保持 `InventoryRepository`、`StockMovementRepository` 接口稳定，新增数据库实现替换当前内存实现。
4. 库存余额表使用 `quantity >= 0` 约束和 `version` 乐观锁字段。
5. 库存流水表只增不改，所有库存变更必须写流水。
6. 为后续 MQ/Webhook 引入 Outbox 表，避免库存写库和事件发布双写不一致。

## 影响

- Service 层业务编排不应依赖具体存储实现。
- 迁移脚本成为代码评审的一部分。
- 后续引入数据库仓储时，需要补充集成测试和并发扣减测试。

## 备选方案

- 只使用 ORM 自动建表：开发快，但生产可审查性和迁移可控性不足。
- 直接拆微服务：过早增加部署复杂度，不利于先稳定库存模型。
- 继续内存实现：无法满足重启恢复、审计和并发一致性要求。
