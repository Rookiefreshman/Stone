# Skill 流与 Token 优化方案

## 1. 目标

WMS 项目会逐步包含业务、架构、数据库、接口、测试、部署、运维等大量上下文。为了避免每次任务都把全部文档塞入 prompt，本项目采用“init 最小上下文 + 专项 Skill + 按需文档”的工作流。

## 2. 推荐 Skill 流

### 业务分析 Skill

适用任务：梳理新流程、补充业务规则、拆分用户故事。

输入：

- 业务场景。
- 涉及角色。
- 上下游系统。
- 异常与边界。

输出：

- 流程步骤。
- 领域对象。
- 状态机。
- 验收标准。
- 对 API/数据模型/测试的影响。

### 架构设计 Skill

适用任务：引入数据库、MQ、缓存、权限、拆模块。

输出：

- 当前架构影响面。
- 目标架构图或文字拓扑。
- 关键技术选型。
- 迁移步骤。
- 风险与回滚策略。

### 代码实现 Skill

适用任务：实现接口、服务、领域规则。

固定步骤：

1. 读取 `init.md`。
2. 定位相关代码。
3. 先写或更新测试。
4. 实现最小变更。
5. 运行相关测试。
6. 更新文档或示例。

### 测试设计 Skill

适用任务：补充单测、集成测试、验收测试、性能测试。

输出：

- 测试矩阵。
- Given/When/Then 用例。
- Mock/Stub/Testcontainers 策略。
- 数据夹具。
- 覆盖风险。

### 文档维护 Skill

适用任务：需求变更、接口变更、架构演进后同步文档。

输出：

- 更新的文档清单。
- 变更摘要。
- 新旧行为差异。
- 示例请求/响应。

## 3. init.md 使用方式

`init.md` 是仓库的入口索引，不追求完整，只追求“够模型快速判断下一步读什么”。建议每次大变更后更新：

- 当前已实现能力。
- 当前未实现边界。
- 代码结构变化。
- 重要业务约束。
- 任务路由。

## 4. Token 优化技巧

1. 先读 `init.md`，不要默认读取全部 docs。
2. 单次任务只加载一个业务域的文档。
3. 大文档按章节维护，任务只引用相关章节。
4. 将重复约束沉淀到 init 或 Skill，减少 prompt 重复描述。
5. 代码任务优先用 `rg` 定位符号，而不是遍历全部文件。
6. 需求讨论使用结构化模板，避免长段自然语言反复解释。
7. 对已有结论做摘要快照，长会话中用摘要替代原始对话。

## 5. 推荐需求模板

```text
背景：
目标：
涉及流程：入库/出库/盘点/补货/主数据/集成
业务规则：
异常场景：
接口影响：
数据影响：
测试要求：
不做范围：
```

## 6. 推荐实现提示词

```text
请先读取 init.md，并只按需读取相关 docs。我要实现【功能名】。
请按以下顺序工作：业务影响分析 -> 测试用例 -> 最小代码实现 -> 文档更新 -> 运行测试。
保持 HTTP 入口/Service/Domain/Repository 分层，不要把业务规则写在 HTTP 入口。
```

## 7. 长期优化

- 为入库、出库、盘点、库存、设备集成分别建立更细的 Skill。
- 为 API、DB schema、事件契约生成独立索引文件。
- 使用 ADR 记录关键架构决策，避免重复讨论。
- 将测试数据夹具文档化，减少每次构造样例的 token。
